# Hosting

## Database: MonsterASP.NET, SQL Server 2025 (decided 2026-08-26)

Live and in use, not just researched. Created on the FREE plan
(`db65520.databaseasp.net`, EU/Germany datacenter — Free plan only offers
EU). EF Core connects to it directly, including from local dev — see
"Local development" below.

Why SQL Server over MySQL (the other free option): this is a C#/.NET
project specifically to build .NET skills for the job market, and SQL
Server is what pairs with .NET/enterprise roles in practice, plus it has
first-party EF Core support. MySQL is more broadly used across the *whole*
market (open source, PHP/Node/web-dev ubiquity), but that's not this
project's stack.

Free-plan limits worth remembering (from MonsterASP's own plan page): low
performance servers, 1GB disk max, limited traffic/features, EU
datacenters only, "not recommended for production" — fine for building and
learning, revisit before anything with real users depends on it.

Two connection modes MonsterASP exposes:
- **Local access** — only reachable from apps hosted on MonsterASP itself
  (their internal network). Not usable from a home dev machine.
- **Remote access (for SSMS)** — public internet access, what local dev
  and any external CI need. Enabled for this database. Connection string
  lives in `dotnet user-secrets` on the dev machine, never in a committed
  file — see `docs/GIT_WORKFLOW.md`.

## Backend hosting: MonsterASP.NET, live (decided 2026-08-26)

Deployed and reachable: `https://english-c1-api.runasp.net` (FreeSite
plan, EU/Germany, `.NET 8` in-process hosting via IIS/ANCM). `/health`
returns 200; HTTP redirects to HTTPS (Let's Encrypt cert, auto-renewing).

**Deploy method: SFTP**, not WebDeploy or Git deploy — SFTP needed no
extra tooling installed (Windows already ships an SSH/SFTP client);
WebDeploy would've needed installing Web Deploy/msdeploy locally, and Git
deploy needs a GitHub repo wired up, neither done yet. Deploy steps:

```powershell
cd client-backend/src/EnglishC1.Client.Api
Remove-Item -Recurse -Force bin, obj, publish-output -ErrorAction SilentlyContinue
dotnet publish -c Release -o publish-output
# re-add ConnectionStrings__AppDb and Jwt__SigningKey to publish-output/web.config (see below) before uploading
scp -r publish-output/* site87751@site87751.siteasp.net:wwwroot/
```

**Always delete `bin`/`obj`/`publish-output` before publishing for a real
deploy.** Reusing the folder across publishes once left a stale
`System.IdentityModel.Tokens.Jwt.dll` (an old version that didn't match
`deps.json`) sitting in `publish-output/`, silently uploaded to
production, and crashed every request — see
[errors/2026-08-27-stale-publish-output-dll-mismatch.md](errors/2026-08-27-stale-publish-output-dll-mismatch.md).
A clean rebuild is cheap insurance against this.

**If the app locks its own DLLs during upload** ("`dest open ... Failure`"
on specific files while the rest upload fine): the running process still
has them open. Upload an empty `app_offline.htm` to `wwwroot/` first —
IIS/ANCM stops the app and releases the locks — then re-run the `scp -r`,
then delete `app_offline.htm` (via an interactive `sftp` session, `rm
wwwroot/app_offline.htm` — `scp` itself can't delete remote files) to
bring the site back.

("Permission denied" on `runtimes/*` directory metadata during `scp -r`
is expected/harmless — the shared host blocks changing directory
timestamps over SFTP; every actual file still transfers.)

**Diagnosing a live 500 with no detail**: MonsterASP's control panel
(`admin.monsterasp.net` → the site → **Logs**) has two tabs that beat
SFTP-ing raw log files by hand — **Event logs** (IIS/System level: app
pool recycles, crash summaries) and **ASP.NET Core debug** (the app's
actual captured stdout/stderr, full .NET stack traces included, works
regardless of `web.config`'s `stdoutLogEnabled`). Check these first.

**Production connection string**: not in any file in the repo, and not in
`dotnet user-secrets` either (that's local-machine-only, never deployed).
It lives as an `<environmentVariable name="ConnectionStrings__AppDb" ...>`
entry inside `wwwroot/web.config` **on the server only** — added by
editing the `dotnet publish`-generated `web.config` locally (reading the
value out of the developer's own `user-secrets`, never pasted anywhere)
and re-uploading it via `scp`. The double-underscore
(`ConnectionStrings__AppDb`) is .NET config's convention for binding an
environment variable to a nested config section. Re-do this step any time
`web.config` gets regenerated by a fresh `dotnet publish` (it doesn't
carry the env var forward automatically) and re-deployed. Same for
`Jwt__SigningKey`, added 2026-08-27 — both variables need re-adding on
every future redeploy, not just one. **As of 2026-08-27, both are live
and verified**: `/health` → 200, a real `POST /api/auth/register` against
the production database succeeds end-to-end.

## Local development

The app talks to the real MonsterASP database directly — no local
database server needed day to day. `docker-compose.yml` (Postgres, port
5433) is kept only as an **offline fallback**; it does not start
automatically (`scripts/start-dev.ps1` no longer launches it). If you ever
need to work without internet access, `docker compose up -d` it yourself
and swap the connection string — but note the app currently targets SQL
Server (`UseSqlServer`), so a Postgres fallback would need the Npgsql
provider back too; not wired up right now since it wasn't needed once the
real database was live.
