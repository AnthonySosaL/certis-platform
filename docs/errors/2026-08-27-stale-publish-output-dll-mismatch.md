# Production 500s: stale DLL in `publish-output/` didn't match `deps.json`

**Date:** 2026-08-27
**Area:** client-backend deploy (MonsterASP.NET)

## Symptom

After finally getting the JWT signing key onto the server, `/health` and
every other endpoint returned a bare `500` with no body - worse than
before, when at least `/health` worked. IIS's Event Log showed repeated
`AppPool Restart` entries ("An ISAPI reported an unhealthy condition"),
consistent with a crash loop, but no fresh detailed exception.

## Root cause

Found via MonsterASP's control panel: **Logs -> ASP.NET Core debug**
(`Files/Logs` in the left sidebar) - this captures the app's real stdout,
including startup exceptions, independent of the `web.config`
`stdoutLogEnabled` setting, and turned out to be far more useful than
SFTP-ing the raw log files by hand (see "How to avoid it again" below).
It showed:

```
System.IO.FileNotFoundException: Could not load file or assembly
'System.IdentityModel.Tokens.Jwt, Version=7.1.2.0, ...'. The system
cannot find the file specified.
   at Microsoft.AspNetCore.Authentication.JwtBearer.JwtBearerOptions..ctor()
```

Checked the local `publish-output/System.IdentityModel.Tokens.Jwt.dll`
that had just been uploaded: its `FileVersion` was **6.35.0.41201**, but
`EnglishC1.Client.Api.deps.json` (built from the actual `PackageReference`
graph) pinned **7.1.2**. The `publish-output/` folder had been reused
across many `dotnet publish` calls this session without ever being
deleted first, and somewhere along the way it ended up with a stale copy
of that one assembly that a later `dotnet publish` never overwrote -
exactly the mismatched DLL got uploaded to the server both times (the
first full deploy, and the app_offline-protected retry), so every request
that touched JWT auth (which is nearly everything - `UseAuthentication()`
initializes the default scheme for **every** request, not just
`[Authorize]` ones) crashed with an unhandled exception, and IIS/ANCM
kept recycling the pool trying to recover.

## Fix

Deleted every `bin/`, `obj/`, and `publish-output/` folder across all
four backend projects, then ran `dotnet publish -c Release -o
publish-output` completely fresh. Verified the rebuilt
`System.IdentityModel.Tokens.Jwt.dll` now reports `7.1.2.41121`, matching
`deps.json`. Redeployed via the `app_offline.htm` dance (see
`HOSTING.md`) since the DLLs are locked by the running process otherwise.
Verified end-to-end against the live server: `/health` -> 200,
`POST /api/auth/register` -> 200 with a real JWT, against the real
production database.

## How to avoid it again

- **Always delete `publish-output/` (and `bin`/`obj`) before a production
  `dotnet publish`**, don't just let it get overwritten in place - an
  incremental publish is not guaranteed to replace every file, especially
  after packages changed versions mid-session. A clean folder plus a
  fresh publish is cheap insurance.
- **MonsterASP's control panel has real diagnostics**, found this session
  for the first time: **Logs -> Event logs** (IIS/System-level: app pool
  recycles, crash summaries) and **Logs -> ASP.NET Core debug** (the
  actual captured stdout/stderr with full .NET stack traces, works
  without needing `stdoutLogEnabled` in `web.config` or an SFTP round
  trip). Check these first next time before reaching for SFTP log
  downloads - much faster.
- `web.config` gets fully regenerated by every `dotnet publish` (it does
  not carry forward the `<environmentVariables>` block) - both
  `ConnectionStrings__AppDb` and `Jwt__SigningKey` need re-adding after
  every fresh publish, before every redeploy. Already noted in
  `HOSTING.md`, worth restating here since it bit us again mid-diagnosis.
